Numbers are Gold+ VIPs (569), data up to 2026-10-20.

## 1. The core problem: two "brains" that disagree

| | Database rules layer | What the pages actually use |
|---|---|---|
| Where | `crm_rules` table + `v_vip_status_base`, `v_vip_priority`, `v_vip_early_warning`, `v_vip_next_step`, `v_recall_attribution` | `vip_members.activity_status`, `churn_risk`, `days_inactive` (set by `refresh_days_inactive()`), plus thresholds hard-coded in each page |
| Used by pages | **None** (`crm_rules` is read by 0 files; the status/priority/recall views by 0 pages) | Churn Urgency, At Risk, All VIPs, Today, Follow Up, Boss View, Alerts, tasks, notification bell |
| Active | deposit ≤ 2 days | deposit ≤ 7 days |
| Resting / still playing | **Balance play** = bets in last 2 days, no deposit | does not exist — betting players are counted as inactive |
| At risk / churn / dormant | 3 / 7 / 15 days (matches CLAUDE.md) | Watch 8–14, At Risk 15–30, Dormant 30+; HIGH risk = 30+ days or win > 20k; MEDIUM = 15+ |

Result: only ~303 of 569 VIPs get the same status from both. Examples:
- 34 VIPs are "At risk" by the rules but shown as **Active** on pages.
- 39 VIPs are **Balance play** (still betting, just not depositing — the "resting, not gone" case). Pages call 22 of them Active and **17 of them At Risk / Watch / Dormant**.
- 39 are "Churn" (7–14 days) but pages show "Watch".

Even "active" has 4 meanings: deposit+bet (KPI, campaigns, last_deposit_date since today), bet only (system reactivation), bet OR deposit (`get_last_active_dates`), deposit only (old last_deposit_date, fixed today).

**Marcus's point is correct:** deposit alone cannot tell "resting" from "left". The rules layer already tracks both `last_active_date` (any bet) and `last_deposit_date`; the pages just don't use it.

## 5. Proposed closed loop

```
CSV import (daily)
  → refresh: one status per VIP from crm_rules
      Active (deposit ≤2d) · Resting/Balance play (betting, no deposit) · At risk 3–6 · Churn 7–14 · Dormant 15+ · Lost 180+
  → daily auto tasks per host (from v_vip_priority P1/P2/P3, skip Active/Resting, skip contacted ≤2d)
  → host contacts (every WA button auto-logs, same popup everywhere)
  → outcome: Replied / No reply + next follow-up date (default by stage) ; 3 no-replies → Unreachable → switch channel
  → result: deposit within 2 days = recalled (by layer) → task auto-closed with result
  → KPI: recall rate per host per layer; reactivation only if ≥7 days truly inactive before
  → thresholds tuned in crm_rules → back to the top
```

## 6. Fix plan (in order)

1. **One status everywhere (DB).** `refresh_days_inactive()` writes `activity_status` / `churn_risk` / `days_inactive` from `crm_rules` using both last bet and last deposit, matching `v_vip_status_base` (add "Balance play/Resting"). Every page then agrees without page changes. Count from data date, not calendar date.
2. **Pages show Resting.** Churn Urgency, At Risk, Today, Retention Queue, All VIPs, Boss View: show "Last bet" next to "Last deposit", and a 😴 Resting tag; remove hard-coded day numbers.
3. **Tasks run by themselves.** Daily cron after import creates host tasks from `v_vip_priority`; auto-close with result; fix `tasks` policies to staff only.
4. **Every contact logged + next step.** Shared WA popup (auto-log, Undo) on all pages; after logging ask Replied / No reply + follow-up date; show Unreachable.
5. **Honest KPIs.** Reactivation = ≥7 days truly inactive before + came back; split "after contact" vs "came back by themselves"; recall rate by layer from `v_recall_attribution`.
6. **Roles + cleanup.** Hosts → `host` role, remove/disable Test Admin, drop duplicate indexes/cron, remove unused tables after a check.

## 7. Decisions (Marcus, 2026-10-21)
- **Resting / Balance play** = bet in the last 2 days but no recent deposit (`crm_rules.balance_play_days` = 2). No churn alert while Resting; once betting stops 3+ days, the normal clock from last real deposit applies.
- **Thresholds everywhere** = 3 / 7 / 15 days since last real deposit (At risk 3–6, Churn 7–14, Dormant 15+), read from `crm_rules`.
- **Daily tasks** = after each import, per host: P1/P2 VIPs from `v_vip_priority`, skipping Active, Resting and contacted ≤ 2 days, max ~20 per host per day.
- **Reactivation KPI** = keep the current rule (bets resume after 3 zero-bet days, credited to the assigned host). Do not change fix 5's reactivation definition.
